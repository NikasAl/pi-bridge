# pi-bridge

Минималистичный доступ к [pi coding agent](https://pi.dev) с телефона через браузер:
одна страница с живым логом сессии (стриминг текста, tool-calls), маркдауном,
полем ввода с поддержкой steering/follow-up и панелью параллельных сессий.
Без файлов, терминалов и мульти-проектов.

Архитектура:

```
телефон ──HTTPS──> nginx на VPS (TLS + basic auth) ──LAN──> pi-bridge (ноутбук)
                                                             └─ N процессов `pi --mode rpc`
                                                                (по одному на сессию)
```

Своей авторизации у моста НЕТ — доступ закрывает nginx (basic auth). WebSocket
живёт по пути `/ws`, страница — `/`, health-check — `/healthz`.

## Файлы

| Файл | Назначение |
|---|---|
| `server.js` | Node-сервер: WS-мост к `pi --mode rpc`, управление сессиями, раздача страницы |
| `index.html` | единственная страница (мобильная вёрстка, лог, сессии, статус-строка) |
| `md.js` | компактный XSS-безопасный рендер Markdown (браузер + Node для тестов) |
| `test/fake-pi.js` | эмулятор RPC-протокола pi — для теста без pi и без токенов |
| `test/smoke.js` | smoke-тест: базовый цикл, ресинк без дублей, мульти-сессии, preferred session, md |
| `pi-bridge.service` | опциональный systemd user-юнит |

## Установка (Arch Linux)

Требуется Node.js >= 20 (проверено на 24) и установленный pi (`pi --version` работает).

```bash
sudo pacman -S nodejs npm        # если ещё нет
mkdir ~/pi-bridge && cp -r <файлы> ~/pi-bridge/
cd ~/pi-bridge && npm install    # ставит единственную зависимость: ws
node test/smoke.js               # опционально: проверка моста без pi (должно быть SMOKE OK)
```

## Запуск

Простой способ (nohup):

```bash
cd ~/pi-bridge
PI_BRIDGE_CWD=/путь/к/проекту nohup node server.js > bridge.log 2>&1 &
```

Мост поднимется на `0.0.0.0:8765` и сам запустит `pi --mode rpc` в указанном каталоге.
Проверка: `curl -s localhost:8765/healthz` → `{"ok":true,"piRunning":true,...}`.

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PORT` | `8765` | порт HTTP/WS |
| `HOST` | `0.0.0.0` | слушающий интерфейс |
| `PI_BRIDGE_CWD` | текущий каталог | рабочий каталог pi-сессии (проект) |
| `PI_BRIDGE_CMD` | `pi` | команда (для тестов: `node`) |
| `PI_BRIDGE_ARGS` | `--mode rpc` | аргументы pi |
| `PI_BRIDGE_SESSION_DIR` | — | добавит `--session-dir <dir>` |

Быстрый тест всей цепочки без реальной pi:

```bash
PI_BRIDGE_CMD=node PI_BRIDGE_ARGS="$(pwd)/test/fake-pi.js" node server.js
```

Полный smoke-тест (без браузера): `npm test` — проверяет базовый цикл,
отсутствие дублей после переподключения, мульти-сессии, preferred session
(остаться на своей сессии после сна/перегрузки) и рендер md.js.

Опционально systemd user-юнит (автозапуск и рестарт):

```bash
mkdir -p ~/.config/systemd/user && cp pi-bridge.service ~/.config/systemd/user/
# поправьте в юните пути и PI_BRIDGE_CWD, затем:
systemctl --user daemon-reload
systemctl --user enable --now pi-bridge
loginctl enable-linger $USER   # работать и без активного логина
```

## nginx (VPS <your-domain.example>)

Файл паролей (если ещё нет):

```bash
printf 'vasya:%s\n' "$(openssl passwd -apr1)" | sudo tee /etc/nginx/pi-web.htpasswd
```

Блок внутри существующего `server { ... }` для 443:

```nginx
location = /piweb { return 301 /piweb/; }

location /piweb/ {
    auth_basic "pi";
    auth_basic_user_file /etc/nginx/pi-web.htpasswd;

    proxy_pass http://<IP-ноутбука>:8765/;   # слэш в конце срезает префикс /piweb/

    proxy_http_version 1.1;                  # WebSocket:
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";

    proxy_set_header Host $host;
    proxy_read_timeout 3600s;                # не рвать WS, пока агент думает
    proxy_buffering off;                     # живой стриминг без рывков
}
```

`sudo nginx -t && sudo systemctl reload nginx`.

Важно: префикс безопасен — страница подключает WebSocket относительным путём
(`/piweb/ws` → nginx срезает до `/ws`), авторизация распространяется и на WS-handshake.

## Проверка с телефона

1. `https://<your-domain.example>/piweb/` → окно basic auth (логин/пароль из htpasswd).
2. Статусная строка: зелёная точка, модель, `ctx 30% (60k/200k)` (контекст из
   `get_session_stats`), `мысли medium` (уровень размышлений из `get_state`).
3. Подгружается история сессии (`get_messages`); после обрыва связи лог
   пересобирается из истории целиком — ни дублей, ни пропусков.
4. Введите сообщение → `Отправить`: уйдёт как `prompt` (если агент простаивает)
   или как `steer` / `follow-up` (переключатель появляется, пока агент работает).
5. Кнопка «стоп» отправляет `abort`; «сессии» открывает панель сессий.

## Сессии (панель «сессии»)

- **Новая сессия** — отдельный процесс pi (параллельно можно держать несколько);
- **переключение** — клик по имени; активная подсвечена, у работающих бейдж;
- **переименование** — кнопка «переим.» (через `set_session_name`, персистентно в pi);
- **удаление** — кнопка «удалить»: процесс останавливается, файл сессии
  (`get_state.sessionFile`) удаляется с диска;
- **автоимя** — первая пользовательская фраза становится именем сессии
  (обрезается до 48 символов), можно переименовать вручную;
- **помнит сессию** — активная сессия хранится в `localStorage` страницы и
  передаётся при подключении (`/ws?session=<id>`): после гашения экрана
  телефона / перезагрузки страницы клиент остаётся на той же сессии,
  а не скатывается на первую; если сессии больше нет — фолбэк на первую.
  (После рестарта самого моста старые id недействительны, и фолбэк срабатывает.)

Управляющие команды моста (можно дёргать и вручную через wscat):
`bridge_create_session`, `bridge_attach {session}`,
`bridge_rename_session {session,name}`, `bridge_delete_session {session}`,
`bridge_list_disk_sessions {force}`, `bridge_open_session {file}`.

## Сессии с диска (продолжение прошлых сессий)

RPC-команды «список сессий» у pi нет, поэтому мост сам сканирует каталог
сессий: `PI_BRIDGE_SESSION_DIR`, а если он не задан — `~/.pi/agent/sessions/`
(включая групповые подкаталоги `--<путь-проекта>--`). Для каждого `.jsonl`
читаются заголовок (`id`, `cwd`), последнее имя из записей `session_info`
(или текст первого user-сообщения, если сессия безымянная) и mtime. Список
кэшируется на 30 секунд; кнопка «обновить» форсирует перескан.

В панели «сессии» ниже активных показывается раздел **«На диске»**: имя,
дата (mtime), бейдж «открыта» у уже подключённых. Клик по строке:

- сессия ещё не открыта → мост спавнит НОВЫЙ процесс `pi --mode rpc
  --session <file>` — сессия продолжается со всей историей (то же, что
  `pi --resume` в TUI, но без пикера);
- сессия уже открыта → клик просто переключает вас на её мост-сессию.

Повторное открытие одного файла двумя процессами отклоняется (иначе два pi
писали бы в один JSONL). Если каталог проекта из заголовка сессии удалён —
pi вернёт ошибку открытия, она попадёт в лог моста.

## Картинки

Кнопка скрепки у поля ввода открывает выбор фото (камера или галерея — обычный
`<input type="file" accept="image/*" multiple>`). Перед отправкой страница
сжимает картинки на клиенте (длинная сторона 1024px; PNG остаётся PNG для
скриншотов, «тяжёлый» PNG и прочие форматы уходят в JPEG q0.85) — это экономит
и мобильный трафик, и токены.

Отправка — нативным полем RPC: `prompt` / `steer` / `follow_up` принимают
`images: [{"type":"image","data":"<base64>","mimeType":"image/png"}]`
(ImageContent). pi сам нормализует mime, пережимает под лимиты модели
(~2000px / 4.5МБ, до ~20 картинок на сообщение) и кладёт картинку в файл
сессии. Если у модели в `get_state.model.input` нет `"image"`, кнопка прикрепа
гаснет.

Экономия на истории: мост вырезает `data` из всех image-блоков в событиях и
`get_messages` перед бродкастом (остаются `mimeType` и флаг `dataStripped`) —
иначе каждое переподключение телефона качало бы мегабайты base64 заново.
В логе такие картинки показываются заглушкой «🖼 image/jpeg».

Ограничение WS: дефолтный `maxPayload` у `ws` — 100 МБ, так что даже несколько
сжатых картинок на сообщение помещаются с запасом.

## Что умеет страница

- стриминг: text_delta, размышления (свёрнуты), tool-calls со статусом и результатом;
- маркдаун в ответах ассистента: заголовки, списки, код (fenced и инлайн),
  жирный/курсив, ссылки, цитаты; во время стриминга — plain text, маркдаун
  применяется к завершённому сообщению; HTML в данных экранируется;
- строка статуса: модель · занятый контекст (из `get_session_stats`, обновляется
  после каждого хода) · уровень мышления (из `get_state`);
- steering: во время работы агента сообщение уходит в очередь (`steer`),
  опционально `follow-up`; счётчик очереди из `queue_update`;
- автопереподключение с backoff + мгновенное при возврате на вкладку
  (телефон рвёт WebSocket при блокировке экрана — это нормально); повторный
  `connect()` идемпотентен — параллельные сокеты невозможны (причина «задвоений»);
- история сессии при каждом подключении пересобирается заново (clear + rebuild);
- неизвестные типы событий показываются свёрнутым raw-JSON — ничего не теряется.

## Отладка

- `curl -s localhost:8765/healthz` — жив ли мост и процесс pi;
- `bridge.log` — stdout/stderr pi и события моста;
- pi stderr виден и в интерфейсе (красные системные строки);
- вручную поговорить с RPC: `wscat -c ws://localhost:8765/ws` и отправить
  `{"type":"get_state"}` (команды протокола: docs/rpc-commands.md в репозитории pi).

## Безопасность (кратко, подробности в чате)

pi по умолчанию YOLO — агент выполняет bash без подтверждений. Тот, кто прошёл
basic auth, получает фактически shell на ноутбуке. Поэтому: длинный случайный
пароль, только HTTPS, fail2ban на 401, порт 8765 не выставлять наружу (firewall —
только LAN/адрес VPS).

## Ограничения

- сессии живут, пока жив процесс моста: после его рестарта остаётся одна пустая
  сессия, НО прошлые сессии теперь можно переоткрыть из панели «На диске»
  (файлы сессий pi на диске сохраняются; открыть конкретный файл можно и
  raw-командой `bridge_open_session {"type":"bridge_open_session","file":"..."}`);
- один рабочий каталог (PI_BRIDGE_CWD) на все сессии; несколько проектов =
  несколько экземпляров моста на разных портах;
- маркдаун рендерится для завершённых сообщений; во время стриминга — plain text;
- удаление сессии необратимо: процесс убивается, файл сессии удаляется с диска;
- extension_ui_request (UI-взаимодействие расширений pi) не поддерживается —
  отображается как системное событие;
- вывод `tool_execution_update` (промежуточный вывод инструментов) не спамится
  в лог, показывается только финальный результат.
